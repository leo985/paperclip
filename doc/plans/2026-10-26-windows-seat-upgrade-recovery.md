# 普通席位升级中断恢复修复

## 现场证据与原因

张志林席位升级后停止心跳，Windows 计划任务为 Ready；`harness online` 返回“席位有未结束的升级”。保留的升级记录中，旧目录为 `dd68bcf9c10b57b2`，目标目录为 `0bc439e27fa760b2`，`noService=false`，`migrationId` 为空。

普通 outbound 客户端更新不改变服务器接入方式，正常就没有 transport migration ID。但旧恢复入口把所有未完成事务均当作 SSH → outbound 迁移，要求非空 migration ID，导致合法普通升级记录不能恢复。`online` 同时拒绝绕过该记录，造成恢复死路。这证实了升级恢复缺陷；首次升级为何中断仍需现场进一步验证，不将此缺陷描述为首次后台启动失败的唯一原因。

## 修复

- 对当前 outbound 席位，允许用无 migration ID 的本地事务记录恢复版本更新；不调用服务器接入方式迁移接口。
- 继续核对席位身份、服务管理选项、备份路径、待恢复客户端目录和旧／新计划任务目标。SSH 席位缺少 migration ID、席位忙碌或遇到未知任务时拒绝修改。
- 先恢复原事务，再单独开启新事务更新到当前网站发布版本；分别持有并释放升级锁，保留各轮备份。
- `online` 的提示明确要求执行 `harness upgrade` 恢复，不要求用户猜测操作或删除记录。

## 验证

- 新增 8 项恢复回归：普通更新无迁移编号、已切换新版服务／入口、恢复后继续更新最新包、忙碌拒绝、未知服务拒绝、SSH 缺迁移编号拒绝、不同席位拒绝、新服务停止失败后保留记录并可重试。
- 本机完整桥测试 116 项：115 通过，1 项 Windows 原生测试因平台不符跳过。
- 按线上基线制作包，仅更新 `seat_upgrade.py` 和 `seat_lifecycle.py`；其他内容及安装器保持不变。
- 发布包 107 项测试：106 通过，1 项 Windows 原生测试跳过。未加入依赖尚未发布模块的 `test_delivery_execution.py`。
- 已确认真实 Windows 现场的升级记录形态；修复后的 Windows 计划任务和持续心跳仍待现场运行命令验证，不以模拟测试替代。

## 恢复操作

保留所有配置和升级记录，不重新登记席位。在原 Windows 用户下执行：

```powershell
& "$env:LOCALAPPDATA/ZhiyanSeat/bin/harness.cmd" upgrade
```

该命令的升级入口下载网站当前安装器，由新包中的恢复逻辑处理旧记录。无需邀请码。完成后执行 `harness doctor`，并由服务器验证最新版本的持续心跳。如果升级仍失败，保留终端输出及 `watcher.log` 进一步诊断，不删除 marker 绕过保护。

## 发布范围

只更新静态客户端 ZIP 与摘要，平台及其他服务不重启，数据库不修改。发布校验与备份位置记录在同名 `-release.json`。
