# 复用 DSP 既有工单的测试返工（2026-11-19）

组织在条目拆分时已有编码、代码评审及功能测试子单，不存在额外修复单/重测单，也不为后续问题重新创建代码评审单。本次废止原四类 Jira 建单方案。

## 当前行为

- 测试 Agent 仍提交逐条失败记录、模块、复现步骤、预期/实际及被测版本。问题保留在正式测试报告、原任务上下文与返工历史中，平台不自动新建 Jira 缺陷单。
- 服务端按模块路由及同主单关系唯一定位原编码任务、原代码评审任务和失败的原功能测试任务。保留 Jira 单号、Paperclip 任务 ID、原生工作流及席位；只生成新的 dispatch/run，原证据留在历史中。
- 复用既有进程退出核验和重开协议。原编码单按 coding/feature 修改并交付新构建，原代码评审单复审，原功能测试单回归；测试仍须全部通过并进入人工验收。连续两轮失败也不增加任何工单或任务。
- 用例任务及未涉及的编码分支保持完成；当前功能测试额外等待本轮原代码评审，防止因旧用例节点已完成而提前回归。
- 来源变化、已有交付不具备安全重开依据、原编码单缺失/有多个候选、评审缺失、执行人变化、旧进程未停止、预算/轮数上限均停止并提示核对。不会建新单补足。
- 页面移除各类 Jira 建单类型配置和手填修复/重测单入口，展示原三类工单。旧类型字段仅用于兼容读取；旧 `repairJiraClient` 入口直接拒绝请求，调用前即阻止网络访问。
- 新客户端能力 `delivery-reuse-repair-v1` 用于区分兼容客户端。计划预览、授权及重新派发均检查能力，防止旧客户端误把原编码当作新 bugfix 工作流。

没有数据库迁移。2026-11-19 已发布服务端、前端及兼容客户端分发包；未启动真实交付链、未操作真实 Jira 工单，也未强制升级已安装席位。相关客户端须完成升级并刷新登记后才能执行新返工协议。既有原生 Harness 返工协议可保留原工作流和统计代次；本次未改动其他 Harness 仓库。
