# 2026-11-04 主工单交付编排：设计审核、编码、用例编写与执行

## 用户已确定的规则

- 设计席位负责人审核设计交付。
- 审核通过后，同一主工单下符合条件的编码单可并行执行（用户后续修订），同席位排队。
- 编码阶段结束后，自动通知并派发测试用例编写，完成后接续功能测试执行。
- 设计启动可发送开始通知；人工审核通知应在设计产物提交后发送。

## 主工单持久化流程

复用 `delivery-workflows` 的阶段、交付回执、人工核验、执行授权和恢复机制，不增加独立的设计接续队列。

阶段：设计执行 → 待设计审核 → 多编码单按模板并行或串行执行 → 测试用例编写 → 功能测试执行 → 主工单待验收。

入口须支持已执行中的设计单加入流程，以当前运行及真实主工单身份建立绑定；不强制重跑需求分析。一个主工单只能有一个活动流程。

将编码阶段从单张工单扩展为显式工单序列；所有阶段动作以 taskId/stepId 定位，不以重复的阶段类型定位。

每个阶段保存真实 Jira 父子关系、目标席位/负责人、输入版本、运行、交付证据、审核结论及转移记录。自动派发不等于完成。

## 人工审核和版本

审核入口放在主工单及设计子单页面，展示设计产物、Jira 交付评论、设计版本与待派编码范围。
只有当前设计席位负责人可以通过或退回；钉钉通知链接进入该入口。
审核结论绑定设计产物摘要。设计修订使原结论失效，暂停未启动步骤；修订后重新提交审核。

## 自动派单条件

- 设计有正式交付证据并通过人工审核；源码生成或终端退出不代表设计交付。
- 编码仅包含同一真实主单下类型匹配、未结束、明确绑定席位且通过现有 Jira/平台准入的编码单；不把评审或测试子单当编码单。
- 编码全部成功、相应代码评审证据通过、进程树停止后，派发用例编写。
- 测试用例编写由具备 QA Harness 能力的测试席位执行。可选用例人工审核作为配置项，不静默添加第二个必经人工审批。
- 测试执行必须绑定用例交付版本、被测代码/构建、测试环境及必要授权；缺少环境或构建时等待，不能启动后宣称完成。
- 功能测试通过后主单进入待验收，不自动代替业务验收。

## 运行、通知和恢复

同一阶段允许不同席位并行；同席位编码单排队，全部完成后汇合；离线或忙碌时持久化等待。失败、取消及权限变化暂停流程，不跳过失败项。
人工审核、阶段开始、阻塞失败及最终结果沿用个人/群通知，并在群内 @ 当前阶段负责人。
通知失败与业务审核状态分开记录；通知失败不代表已审核，也不伪造派单成功。
使用流程锁、版本比对和幂等授权；重启恢复原队列，不重复建单或启动。阶段中断只能显式恢复。

## 实施与验证

1. 扩展共享流程契约：设计起步、编码序列、明确 stepId、用例审核配置。
2. 后端配置与推进器：负责人审核权限、真实父子关系、版本门禁、并行汇合或串行推进、停止证明及恢复。
3. 页面：主工单流程卡、设计审核入口、阶段席位/环境配置、待处理入口与错误提示。
4. 接入桥：复用并补齐当前设计/编码/QA 运行与交付回执，不引入第二套完成协议。
5. 回归：设计审核前不启动编码、多编码并行汇合/同席位排队、错父单拒绝、驳回/版本变化暂停、QA 产物版本与环境校验、离线/重启/重复回执不重复执行。
6. 按生产实际依赖准备隔离发布；完整流程尚未上线，不将已有账号关联修复的发布视为本流程发布。
