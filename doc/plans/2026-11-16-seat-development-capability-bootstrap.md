# 席位研发能力首次登记与补登记

日期：2026-11-16。

## 问题与行为

设备接入已登记研发目录，但能力登记为空时旧心跳直接跳过，交付链无法按原生角色匹配席位。接入安装器在运行配置核验后尝试首次研发能力登记；已有席位升级后，空闲心跳每 60 秒尝试从设备登记的默认研发目录补登记。校验失败继续上线并显示固定提示，不声明不存在的技能。

服务端仅允许首次自动登记 development/default，路径必须与该机器的设备登记完全一致，执行环境必须仍为默认环境，不得已存在另一份研发能力。沿用机器凭证、修订比较、事务锁、活动运行阻断、文件校验与审计；executionGranted=false。分析与测试不自动发现，已登记能力的角色变化不放宽。无数据库迁移或新 API 字段。

## 验证

客户端相关测试 69 项通过（首次登记专项 16 项）；服务端能力接口及数据库回归 11 项通过。UI token gates 通过。标准服务端 typecheck 被 Runner 准备流程缺少 cargo 阻断，直接 TypeScript 检查已通过。发布采用线上客户端包为基线，仅合入本次安装器、自动登记模块及使用说明改动，不打包工作区其他业务改动。

## 既有席位处理

在新服务端和客户端包可用后，对当前 DSP7 组织支持网页升级的席位逐一创建固定版本升级请求；忙碌或离线等待原席位，旧客户端不支持网页升级的席位需要本机升级。成功须由目标版本心跳及真实本机能力登记回执确认，不能以请求已排队视为完成。
